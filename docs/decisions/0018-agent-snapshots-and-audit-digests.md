# ADR-0018 草案：Agent 配置和工具的版本管理与审计摘要

状态为草案。2026-11-20 用户明确了目标：内部 Agent 改写配置或工具时形成可追踪的 snapshot，支持类似 Git 的回退、分支切换和合并。审计还应提供模型生成的 digest，呈现变更当时的判断与依据。V01 已完成本地源码核对。V02 和 V03 的合成闭环范围及验收状态见[执行清单](../execution-todo.md#vagent-配置与工具的版本管理与审计)。

## 当前能力与缺口

molt kernel 已有不透明 CAS、manifest、单写者 generation 提交、持久日志、按原 request ID 查询及归档回退。归档回退将原 manifest 作为新 generation 提交，保留激活历史；当前提交日志没有独立的回退意图、授权主体或归档 ID 字段。现有 generation 不足以表达版本父子、分支命名引用与合并。见 [回退实现](../../crates/molt-kernel/src/state.rs) 和 [恢复契约](../research/v2-transaction-state-machine.md)。

## 版本与激活

- 一个可发布的逻辑变更形成一个 snapshot。配置和配套工具进入隔离暂存区，同一变更可以包含多个文件。校验成功后才允许整体激活，失败的候选与检查证据可以保留供审查。
- Snapshot 表示不可变内容树，版本提交引用 snapshot 与父版本。普通变更有一个父版本，合并提交有两个父版本。分支是指向版本的命名引用，历史构成有向无环图。
- 激活记录表达当前实际使用的版本和切换原因。回退记录原活动版本、目标版本及授权证据；切换分支记录目标分支和实际选中的版本。运行中的任务固定使用启动时版本，新任务读取最新活动引用。实现须定义切换时旧版本的保留期，以及运行中引用如何避免 GC。
- 分支推进须以预期旧指针为前置条件，冲突时保留双方候选。合并使用共同祖先，配置/工具的合并结果还须经过组合验证。合并、校验和激活分别留证。
- 调用方在发送提交前持久保存原 request ID 和参数。断线后查询原 ID。重启及并发场景均须保持版本引用与生效状态一致。运行入口必须通过受控提交路径读取已激活版本，明确如何避免 Agent 绕过它直接改生效目录。

## 原始判断、证据与 digest

| 记录 | 建议内容 |
| --- | --- |
| 原始判断 | 变更时由 Agent 显式提交的目标、采用的方案、简短理由、引用依据和未验证假设。授权主体与审批来自受信入口，单独记录来源。 |
| 原始证据 | 变更前后版本、文件或配置键、实际执行的检查及结果、审批记录和运行反馈。按权限提供受控引用，保留证据来源和完整性绑定。 |
| 模型 digest | 描述行为变化及影响，区分原始判断、模型推断和待验证问题。每个关键结论链接对应证据；记录所用模型、生成时间、模板版本和输入证据集合。重新生成时保留历史 digest。 |

模型 digest 可异步生成，其状态独立记录。审计仍能读取原始判断与证据。模型输出不得自动成为授权或验证结果，真实凭据和敏感原文不得进入模型。核验时应能从一句结论回到原始判断、对应版本与实际检查，并能看到证据缺失或相互冲突的情况。外部保管的可信 checkpoint 用于验证历史前缀，业务执行真实性仍依赖独立证据。详见[外部集成契约](../operations/external-integration.md)。

## V01 源码核对

下表行号对应本次证据绑定的工作树。

| 入口 | 当前语义与缺口 |
| --- | --- |
| `manifest_create`、`manifest_get`、`current` | manifest 顶层固定为 `roots` 和 `tree_hash`，文件条目含 `type`、`sha256`、`size`、`mode`。UDS `current` 得到恢复后的指针，再以 `manifest.get(hash)`、`object.get(hash)` 按哈希读取。manifest 读取验证规范编码、树哈希及直接对象的内容和大小。[manifest.rs 24–110](../../crates/molt-kernel/src/manifest.rs)、[state.rs 603–649](../../crates/molt-kernel/src/state.rs)、[main.rs 246–289](../../crates/molt-kernel/src/main.rs) |
| `commit_locked`、`commit` | 写锁内先恢复，校验 manifest，检查重复 ID，然后读取实际 `previous`，写 journal、确认日志、更新 `current`。UDS 入参只有 `request_id`、`manifest_hash`、`ts`。两个调用者基于同一旧版本构造的提交可以先后成功，后提交可能覆盖先提交的逻辑更新。锁前再读一次仍有竞态。[state.rs 288–336](../../crates/molt-kernel/src/state.rs)、[main.rs 437–450](../../crates/molt-kernel/src/main.rs) |
| `recover_locked`、`request_status` | 日志段 fsync 后替换并同步 `HEAD`，确认耐久日志前缀。恢复裁掉未确认尾部，按已确认日志与 journal 补写 `current`，遇历史不一致时拒绝。UDS `request.status` 返回原提交的 `committed/result` 或 `not_found/retry_with_same_request_id`。现行请求指纹绑定 manifest 和时间，同 ID 同参返回原 generation，异参冲突。[log.rs 164–241](../../crates/molt-kernel/src/log.rs)、[state.rs 134–205、218–280、288–350](../../crates/molt-kernel/src/state.rs) |
| `archive`、`rollback` | 归档将当前 generation 固定到不可变名称。回退校验归档来自已提交历史，再用其整个 manifest 追加 generation。直接用于应用回退会连同旧分支映射和旧证据索引一起重新发布。[state.rs 353–415](../../crates/molt-kernel/src/state.rs) |
| `gc` | 写锁内先恢复。保留日志的直接 payload，以及所有已确认 generation 和归档的 manifest 与其直接文件对象。GC 不递归追踪 JSON 或嵌套 manifest 的内部引用。上传、创建 manifest 和提交之间有间隙，未提交对象可能被清理。`dry_run` 仍写 `audit/gc-plan.json`。[state.rs 418–529、603–634、652–663](../../crates/molt-kernel/src/state.rs)、[main.rs 234–245](../../crates/molt-kernel/src/main.rs) |

## 首阶段设计建议

**用一个 manifest 发布完整应用状态。** 应用索引作为直接文件，记录格式版本、版本图、分支名到 snapshot ID 的映射、活动 snapshot ID 和审计索引。不可变 snapshot 记录父 ID、配置与工具的内容及依赖标识、组合校验结果和原始证据引用。索引、snapshot 描述和须保留的配置、工具、证据对象都直接列入 manifest 的根条目。一次 generation 提交即发布这些状态。应用层校验引用闭合、版本图和激活策略，kernel 仍只校验不透明文件。应用回退基于最新索引切换活动指针，记录起止版本、授权与验证，追加 generation。保留后来创建的分支和证据。

**用隔离 state 和单一受控写入口复用现行协议。** 由 broker 串行执行读取基线、比对预期 generation 和目标分支旧指针、暂存、校验、提交及未知结果恢复。Agent 提交提案，运行者通过受控读取或只读版本目录取得版本。broker 独占 socket 与 state 写入权限，隔离 CLI、mirror、归档回退和其他 GC 调用。UDS 的 `0600` 保护需要结合身份隔离，同 UID 进程共享权限。暂存到提交或放弃期间与实际 GC 互斥，重启先恢复持久在途意图再开放 GC。冲突时保留候选，显式合并或重新校验后形成新操作。现有 mirror 以 `state` 根承载 v1 迁移，调用无条件提交。[main.rs 103、199–245](../../crates/molt-kernel/src/main.rs)、[kernel_mirror.py 97–165](../../molt/kernel_mirror.py)

**用原 ID 恢复未知结果。** 发送前持久化 state ID、原 request ID、目标 manifest、时间、预期基线及重建材料。断线、超时或提交 I/O 结果不明时，新连接确认 state 身份并查 `request.status`。已提交时核对原 manifest 和 generation，启动新任务另读最新 `current`。恢复后未找到且基线仍符合时，按原哈希补齐必要暂存对象，用原 ID 和原参数重放。基线已变则保留提案并报告冲突。查询失败或身份、结果不符时暂停该写入路径，禁止换 ID 盲重试。[kernel_client.py 18–78](../../molt/kernel_client.py)

**在途任务固定已提交版本。** 启动时只读一次 `current`，绑定 state ID、generation、manifest hash 和 snapshot ID，按该 manifest 验证并物化到隔离的不可变目录。任务重启也用原版本。当前 GC 保留全部已提交 manifest 的直接对象，此路径无需新增 pin。未提交版本、藏在对象内部的引用和外部依赖不受这层保护。未来若允许从暂存版本运行或回收历史，需要在选定版本时原子取得持久 pin，任务结束或明确恢复后释放。第一阶段应限制 manifest 与单次 IPC 帧的规模，现行客户端帧上限为 16 MiB，历史保留会增加存储及全历史校验开销。[kernel_client.py 8–8、46–78](../../molt/kernel_client.py)

**原始证据先提交，digest 后发布。** 激活提交原子绑定原始判断、验证输出、批准来源和证据引用。异步摘要固定目标事件、snapshot 和输入证据清单，记录模型标识、模板版本、生成时间和逐结论引用，标明推断及证据缺失或冲突。摘要写回时重新读取最新索引并通过同一写入路径追加，保留历史。失败时原始证据仍可审计，状态显示待生成或失败。首阶段用确定性 synthetic 结果，模型输入仅使用获准的脱敏投影，展示证据引用时重新鉴权。摘要无授权和验证效力。

## 待决策的最小接口与兼容性

| 方案 | 接口与影响 |
| --- | --- |
| 隔离 state 与单一 broker（建议首阶段） | 复用 `current`、对象上传/读取、`manifest.create/get`、`generation.commit`、`request.status` 及握手返回的 state ID。应用层持久化请求和证据。无需改 IPC、kernel 状态格式或 v1 schema。写入以身份隔离和 GC 互斥有效为前提。 |
| 新增条件提交（需要独立写入口时） | 候选 `generation.commit_if_current` 接收原 ID、目标 manifest、时间、预期 current token。在同一 state 内用 generation 与 log hash 表示基线，支持显式空基线。仅比较 manifest hash 会遗漏回到同一 manifest 的新 generation。恢复后在同一 writer lock 内先处理已提交 ID 的原样重放或异参冲突，再比较基线。失败返回独立的过期基线错误，无新 journal/generation。重放须校验预期 token。可评估从已持久化的 `previous` 复核 token 并隔离新旧请求 ID，保持记录格式。若持久化方法与完整请求指纹，则需版本化解码、能力协商和旧日志、journal、客户端验证。现行 `current_for` 严查四个元数据字段和旧指纹公式。对受管 state 必须封住旧的无条件提交和回退入口。新客户端遇到旧 kernel 时拒绝条件写入。 |
| 暂存对象保护（需要并行 GC 时） | 候选为持久暂存根，由 GC 在同一锁域保留其直接对象，并处理提交、放弃与崩溃恢复。另一候选是在一次 kernel 事务内落地暂存材料和提交，须评估分块上传、临时空间和锁时长。两者都要评估 IPC、状态格式与旧 GC 并用风险；仅增加条件提交仍有上传至提交的清理窗口。 |

用户已授权隔离 state 的 synthetic 闭环，V02 采用单一 broker 方案。本地示例与运行边界见[合成版本闭环](../operations/synthetic-versions.md)。独立写入口与并行 GC 的需求和接口仍待决定。v1 只读审计、显式迁移和冻结 schema 继续适用。业务侧取消或补偿另行授权和查证。

## V03 命名分支与合并

从 `examples/synthetic_versions.py` 的 `activate`、`rollback`、`_switch`、`_publish` 开始，保留 V02 的单一 broker、现有 UDS 和合成状态边界。沿用已有测试覆盖，再补齐以下验收。

- 从已提交 snapshot 创建命名分支。创建分支保留当前活动版本；切换分支记录目标名称、旧活动版本和选中的 snapshot。回退后活动版本与分支头可以不同，分支头保持可追溯。
- 提案带上预期基线与分支头，在 broker 锁内重读并核对。同一旧分支头的两个提案仅一个推进，冲突方能保留候选供核对，未获验证的候选不可激活。
- 以共同祖先合并，记录目标与来源两个父版本。对冲突和配置与工具组合校验失败分别验收；两者都应保留旧分支头与活动版本。合并成功时，将版本、分支引用和证据一起提交，只有显式选择激活时才切换活动版本。
- 对切换和合并覆盖断线后原 ID 恢复、旧任务仍读原版本、审计可追溯至来源版本和实际校验。真实模型 digest、Agent 写入隔离与可并行回收仍待后续决策。

合成实现按配置和工具两个完整对象做三方合并，要求两个不同的父 snapshot 和唯一最近的共同祖先。
选择这一粒度是为了让对象冲突和跨对象组合校验分别可验证。过期的分支推进提案以独立候选文件
保存在私有 sandbox 中。原提交接口和恢复流程足以支持当前单一 broker，后续独立写入口和并行 GC
仍对应上节列出的接口决策。操作示例及边界见[合成版本闭环](../operations/synthetic-versions.md#命名分支和合并)。

## V04–V07 受控写入与真实审计验收

沿用 V03 的版本图和事务底座。Agent 只能通过提案入口提交隔离暂存内容，broker 核对基线与授权并控制 kernel 写权限。受管格式、依赖标识和校验命令应固定，测试覆盖引用越界、未授权写入及隔离控制不可用。对运行版本同时固定配置、工具和受管依赖，外部可变依赖需要显式拒绝或单列限制。

原始判断是变更当时提交的简短理由和依据。校验结果、可信主体及批准来源由各自入口留证。模型输入固定到已提交事件的获准证据投影。摘要落盘前核对引用存在且可访问，核对失败或模型不可用时可继续读取原始记录。生成或重生成均不得覆盖活动版本或其他分支更新。

先用隔离测试进程与确定性替身验收整条链。再以同一入口验证本地实际 Agent 写入、离线真实模型推理、分支合并、原子激活、故障恢复和回退。审计者应能从 digest 逐条追到当时的判断、校验记录、证据内容和实际生效版本。两次验收分开记录，真实本地验收通过前保留实际依赖和未验收项。具体任务与完成条件见 [执行清单](../execution-todo.md#vagent-配置与工具的版本管理与审计)。

## 后续验收用例

| 场景 | 预期 |
| --- | --- |
| 校验、激活、回退 | 校验失败保留旧版，成功时配置与工具一并切换。应用回退追加 generation 和证据，保留后来创建的分支和审计记录。 |
| 并发和分支 | 两个提案使用同一基线仅一个能推进，另一方保留候选。覆盖不同分支更新、回到同一 manifest、分支创建与切换、双父合并及组合校验失败。 |
| 断线和崩溃 | 覆盖 journal 落盘、日志段落盘、HEAD 持久化、current 更新后响应丢失。读者只见整套旧版或新版。原 ID 能区分未提交与已提交，同参无重复 generation，异参冲突，基线前移后不重放陈旧更新。 |
| 旧任务和 GC | 旧任务跨激活、回退、重启及 GC 仍读原版。验证直接对象保留、嵌套引用不会自动保留、暂存与 GC 互斥。获批后再测试暂存根的恢复与释放。 |
| digest 审计 | 摘要结论能回到版本、原始判断、验证和授权，缺失与冲突有标识。并行应用写入不被摘要覆盖，生成失败仍可审计，重生成保存历史。 |
| 权限与兼容 | 绕过受管写入口的调用被拒，未授权证据不进入模型或展示。验证旧 kernel/客户端能力边界、v1 只读审计和迁移源零写入。 |
