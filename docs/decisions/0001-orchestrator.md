# ADR 0001：选外层编排，不写 Pi 扩展

## 背景

molt 要做的是"自动研究循环"：搜索一组受控开关，让本地小模型提案、前沿模型执行、外部测试当裁判，得分字典序，每次改动可回退。上游 Pi 提供 harness 与 SDK/RPC，SoL-Pi 已把四个效率机制做成扩展并暴露 `sol-pi.json`。问题只剩：这层循环写在哪。

## 选项 A：写 Pi 扩展

在 Pi 进程内注册扩展，直接拿到 session 事件、工具调用钩子和上下文，开关以进程内状态存在。

优点：能触达最细的运行时信息，无需跨进程传数据。
代价：扩展跑在 Pi 内部，改一次开关就等于重启或重载 agent，多个候选无法共享一个进程；评测逻辑必须和 harness 生命周期绑死；崩溃会一并带走 agent 与会话。

## 选项 B：外层编排（orchestrator）

molt 以独立 Python 进程存在，把 Pi 当子进程调用：按开关渲染 `sol-pi.json`、spawn、收产物、打分、决定下一版。

优点：候选之间天然隔离，一次失败不污染其它候选；配置、日志、分数都在自己手里。
代价：跨进程传数据，粒度比扩展粗；依赖 Pi 的 CLI/输出格式稳定。

## 决定

选 **B：外层编排**。三条理由：

1. **并行跑候选**。搜索要求同一题集上比较多个候选 config。外层可以并发 spawn 多个 Pi 子进程，各有独立 workdir 与 `sol-pi.json`；扩展内做不到真正的进程隔离。
2. **回退与证据必须在外层**。回退要的是 config 版本 + git tag + runs/ 归档，裁判要的是仓库外的测试脚本与题集隔离。这些都是 Pi 进程之外的东西，放进扩展反而要把外部状态硬拉进 harness。
3. **团队主语言是 Python**。编排、打分、题集管理用 Python 写最快，而 Pi 扩展是 TypeScript/Node 生态，切换成本高、可维护人少。

唯一例外：若某个开关必须读到 Pi 的内部事件才能生效（例如需要工具调用前的钩子），才允许写一个薄扩展，时间盒 3 小时；超时即回到 B，把需求降级成"可由 `sol-pi.json` 表达"。

## 后果

- molt 侧要知道 Pi 的 CLI 参数与输出格式，Pi 升级可能带来兼容成本；`doctor` 子命令负责前置检查。
- token 与耗时只能从子进程产物或 provider 侧统计里拿，精度不如进程内读数，需要在 `docs/contracts.md` 里明确口径。
- 开关只能通过 `sol-pi.json` 与命令行表达；表达不了的维度不得进入搜索空间。
- 评测与环境准备（workdir、题集、判分脚本）全部由 molt 负责，Pi 保持无感。

## 何时重新考虑

满足任一条即重开本 ADR：

- 连续两个迭代都被"需要 harness 内部钩子"卡住，且薄扩展试过仍不够；
- 子进程方案的单题额外开销超过总耗时的 20%；
- Pi 的 CLI/输出格式发生破坏性变更，且适配成本高于改写成扩展；
- 上游 Pi 官方提供了进程内多候选隔离能力。
