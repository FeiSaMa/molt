# ADR 0008：现场演示 `molt demo` —— 1 live 候选 + 1 replay 基线 + 10 题扫描回放

- 状态：已决定
- 日期：2026-11-11
- 关联：`molt/demo.py`（`run_demo` / `record_baseline_scan`）、`molt/cli.py`（`cmd_demo`）、
  `molt/export.py`（`runs[].demo_group`）、`tests/test_demo_command.py`

## 背景

B2-D7 要求现场演示一条**可复算闭环**，而不是「跑两次模型」：

1. 1 条 replay 基线（已录 run 的回放，带 `replay_of_run_id`）；
2. 基线回放的 `SearchHistory` → `Engine.propose` 派生候选；
3. 候选在**同一题**上真实 Pi 运行 1 条（live）；
4. 基线 vs 候选过 `Gate`，按结论 `adopt` 或 `revert`；
5. 10 题扫描是**已录扫描的回放**，在页面与讲解词中单独成组，不是 demo 的第二次运行。

硬约束：端到端 180s；出现超时即失败，不得降级输出；B2 出口必须测量子进程开销比
（ADR-0001 重开条件 2）。

## 决定

1. **证据分组显式化**。`Run.ext.demo_group` 取 `closure` / `scan10` / `candidate-scan`，
   导出层原样带到 `runs.json[].demo_group`（无分组时为 `null`）。
   - `closure`：1 条 replay 基线 + 1 条候选（live 或 replay 模式下的 fixture），同一题
     （demo 缺省 `smoke-add`）；
   - `scan10`：10 条 replay，全部来自已录基线扫描；`replay_of_run_id` 指向录制时的原始 run；
   - `candidate-scan`：候选在其余 9 题上的 **fixture** 执行，只为让 gate / audit 的 10 题
     分母成立，不是 live，也不是第二次 demo 运行。
2. **基线与候选的 provenance 由 run.ext 显式声明**，不靠推断：
   - replay 副本：`ext.provenance = {kind:"replay", replay_of_run_id, group}`；
   - live 候选：`ext.provenance = {kind:"live", model, runtime_id:"pi-1.5.0"}`；
   - 候选其余题：`ext.provenance = {kind:"fixture", note}`，即使 genome 的 runtime 标为 pi
     也绝不被导出层推断成 live（`molt/export.py` 的 fail-closed 规则不变）。
3. **基线来源**：`--baseline-state <dir>` 只读；缺省时在同级 `<state>-baseline` 录制或复用
   一次 fixture 基线扫描（10 题）。复制 run 时**生成新 `run_id`** 并补记同额 ledger，
   源 run 与源 state 不被改写。
4. **gate / audit 口径**：基线侧 10 条 replay，候选侧 9 条 fixture + 1 条 live/replay；
   两侧各 10 题，`molt audit` 可从 run 重算 result / decision / invalid ratio / 账本，
   demo state 自身 `audit.json.ok=true`。
5. **adopt / revert 跟随 gate 结论**：先归档基线（generation 1）；`verdict=adopt` 时归档
   候选（generation 2），否则 `revert` 到基线归档。不为了「演示两个命令」而违背 gate。
6. **180s 硬上限**在 init / baseline / replay / propose / candidate / gate / report /
   adopt-revert / audit / export 每个阶段检查；超时抛 `DemoTimeout`，命令 exit 1，
   **不写导出目录**。
7. **开销比**：live run 用 `time.monotonic()` 包住 `Engine.run_task`（复制工作区 + guard +
   Pi 子进程 + verify + 落盘），Pi 子进程耗时取 `run.usage.wall_ms`；
   `overhead_ratio = (total - pi_subprocess) / total`，阈值 20%。超阈值时仍完成演示，但在
   summary 记 `within_threshold=false` 并在 stderr 提示按 ADR-0001 重开条件 2 复查。
8. **`--mode replay`**：无 Pi、无网络，候选 closure 题也走 fixture，并显式标
   `kind="fixture"`。CI 与零写入测试只跑该模式；live 测试用 `pytest.mark.pi` +
   `MOLT_RUN_PI_LIVE=1` 显式放行。

## 后果

- 页面可以用 `runs[].demo_group` 与 `runs[].provenance` 直接把 closure（1 live + 1 replay）
  与 10 题扫描回放分开渲染，不需要解析 run_id 或时间。
- `demo` 的 live 路径依赖 Pi + trust preflight；auth 不可用时退回 `--mode replay`，
  证据会明确显示 0 live，不存在「假装 live」的中间态。
- 9 条 `candidate-scan` fixture run 会进入 `runs.json`；它们被标为 fixture，页面必须与 live
  分开展示。若未来要让候选扫描也全部 live，需要新的预算与 ADR，不在本决定范围内。
- `runs.json` 新增 `demo_group` 字段是向后兼容的附加字段；旧导出重新生成即可获得。
- `scenario.json` 的 `claim.live_model_calls` 改为由 evidence 计算（存在 `kind=live` 才为 true），
  并新增 `provenance_counts`；fixture-only 导出的 claim 与旧版一致。
