# ADR 0008：现场演示 `molt demo` —— 1 live 候选 + 1 replay 基线 + 10 题扫描回放

- 状态：已决定
- 日期：2026-11-11
- 关联：`molt/demo.py`（`run_demo` / `record_baseline_scan`）、`molt/cli.py`（`cmd_demo`）、
  `molt/export.py`（`runs[].demo_group`）、`tests/test_demo_command.py`

## 背景

B2-D7 要求现场演示一条**可复算闭环**，而不是「跑两次模型」：

1. 1 条 replay 基线（已录 run 的回放，带 `replay_of_run_id`）；
2. 基线回放的 `SearchHistory` → `Engine.propose` 派生候选；
3. 候选在**同一题**上真实 Pi 运行 1 条（live）；
4. 基线 vs 候选过 `Gate`，按结论 `adopt` 或 `revert`；
5. 10 题扫描是**已录扫描的回放**，在页面与讲解词中单独成组，不是 demo 的第二次运行。

硬约束：端到端 180s；出现超时即失败，不得降级输出；B2 出口必须测量子进程开销比
（ADR-0001 重开条件 2）。

## 决定

1. **证据分组显式化**。`Run.ext.demo_group` 取 `closure` / `scan10` / `candidate-scan`，
   导出层原样带到 `runs.json[].demo_group`（无分组时为 `null`）。
   - `closure`：1 条 replay 基线 + 1 条候选（live 或 replay 模式下的 fixture），同一题
     （demo 缺省 `smoke-add`）；
   - `scan10`：10 条 replay，全部来自已录基线扫描；`replay_of_run_id` 指向录制时的原始 run；
   - `candidate-scan`：候选在其余 9 题上的 **fixture** 执行，只为让 gate / audit 的 10 题
     分母成立，不是 live，也不是第二次 demo 运行。
2. **基线与候选的 provenance 由 run.ext 显式声明**，不靠推断：
   - replay 副本：`ext.provenance = {kind:"replay", replay_of_run_id, group}`；
   - live 候选：`ext.provenance = {kind:"live", model, runtime_id:"pi-1.5.0"}`；
   - 候选其余题：`ext.provenance = {kind:"fixture", note}`，即使 genome 的 runtime 标为 pi
     也绝不被导出层推断成 live（`molt/export.py` 的 fail-closed 规则不变）。
3. **基线来源**：`--baseline-state <dir>` 只读；缺省时在同级 `<state>-baseline` 录制或复用
   一次 fixture 基线扫描（10 题）。复制 run 时**生成新 `run_id`** 并补记同额 ledger，
   源 run 与源 state 不被改写。
4. **gate / audit 口径**：基线侧 10 条 replay，候选侧 9 条 fixture + 1 条 live/replay；
   两侧各 10 题，`molt audit` 可从 run 重算 result / decision / invalid ratio / 账本，
   demo state 自身 `audit.json.ok=true`。
5. **adopt / revert 跟随 gate 结论**：先归档基线（generation 1）；`verdict=adopt` 时归档
   候选（generation 2），否则 `revert` 到基线归档。不为了「演示两个命令」而违背 gate。
6. **180s 硬上限**在 init / baseline / replay / propose / candidate / gate / report /
   adopt-revert / audit / export 每个阶段检查；超时抛 `DemoTimeout`，命令 exit 1，
   **不写导出目录**。
7. **开销比**：live run 用 `time.monotonic()` 包住 `Engine.run_task`（复制工作区 + guard +
   Pi 子进程 + verify + 落盘），Pi 子进程耗时取 `run.usage.wall_ms`；
   `overhead_ratio = (total - pi_subprocess) / total`，阈值 20%。超阈值时仍完成演示，但在
   summary 记 `within_threshold=false` 并在 stderr 提示按 ADR-0001 重开条件 2 复查。
8. **`--mode replay`**：无 Pi、无网络，候选 closure 题也走 fixture，并显式标
   `kind="fixture"`。CI 与零写入测试只跑该模式；live 测试用 `pytest.mark.pi` +
   `MOLT_RUN_PI_LIVE=1` 显式放行。

## 实测（2026-11-11，demo-6，真实 Pi 1.5.0，并发 1）

6 组配置各跑 10 道 search（$ 费用为 run 记录实际值；均 10/10、0 invalid、
attempts=1）：

| config | solved | cost | cost_per_solved | wall | 与 low/full 差 |
|---|---|---|---|---|---|
| **low/full（v0，demo 候选）** | **10/10** | **$0.009978** | **$0.000998** | 41.7s | — |
| off/full | 10/10 | $0.012385 | $0.001239 | 53.2s | +$0.002407（+24.1%） |
| off/minimal（最接近） | 10/10 | $0.011894 | $0.001189 | 64.5s | +$0.001916（+19.2%） |
| low/minimal | 10/10 | $0.021180 | $0.002118 | 71.7s | +$0.011202 |
| **high/full（v0-pi，demo 起点）** | **10/10** | **$0.035560** | **$0.003556** | 106.9s | +$0.025582 |
| high/minimal | 10/10 | $0.021113 | $0.002111 | 91.8s | +$0.011135 |

**负结果：6 组中没有「10/10 且 cost < low/full」的候选。** 实际最便宜的是
low/full（$0.009978）；最接近的候选是 off/minimal，仍贵 19.2%。这组数据说明：
demo 采用的高→低起点是**选定的叙事起点**，不是「搜索空间最优」或「baseline v0 被改进」
的声称。

## 现场 demo（adopt：high/full → low/full）

2026-11-11 用同一批真实 state 跑：

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m molt demo --mode live --max-wall 180 \
  --baseline-state state/scan-high-full --candidate-state state/real-baseline \
  --state state/demo-adopt --out web/data
```

- 起点：v0-pi（high/full）10/10，$0.035560，cps $0.003556；
  proposal 从这组 SearchHistory 派生 `low/full`（与候选 state 的 v0 switches 一致）。
- 候选：v0（low/full）10/10，$0.009978；**扫描级**成本 −72%（$0.035560 → $0.009978）。
  gate 用 9 条 replay + 1 条 live closure，合计 $0.010684、cps $0.001068 →
  **gate 级 −70.0%**，`adopt / lower_cost_per_solved`。
- closure：1 live（低配候选，单题）+ 1 replay 基线（v0-pi，带 `replay_of_run_id`）；
  10 题扫描 10 条 replay、其余 9 题 9 条 replay；`provenance_counts` 为 1 live / 20 replay。
- holdout：起点 5/5，候选 5/5（聚合导出）。
- 计时 6.4s / 180s；开销比 4.1%；15 文件；`audit.json.ok=true`。
- 若候选 state 的 genome 只有 fixture runtime（如 v0），closure 会用同 switches 的
  pi-runtime 变体执行，`summary.genomes.candidate.runtime_variant=true` 明确标注；
  gate 的 `candidate_genome_id` 指向该变体，扫描 replay 保留原 genome id。

## 任务饱和与效率 claim

> 模型能力已经碾压这 10 道题；molt 证明的是：在成功率不降的约束下，进化可以发生在成本与墙钟上——high/full → low/full，cost −72%、wall −61%，gate adopt，1 live + 1 replay，证据可复算。

- **题目饱和**：真实 Pi 基线 **10/10**，成功率维度没有 headroom；fixture `3/10` 只是
  `molt calibrate` 的校准口径，不代表真实难度，不得写成真实基线。
- **效率（同一 10 题扫描）**：cost `$0.035560 → $0.009978`（**−72%**）；
  wall `106.9s → 41.7s`（**−61%**）；gate 级 cps `$0.003556 → $0.001068`（**−70.0%**）；
  holdout `5/5 → 5/5`；gate `adopt / lower_cost_per_solved`。
- **负结果**：6 组真实扫描全部 10/10，`low/full` 是最便宜配置，没有候选比它更便宜
  （最接近的 `off/minimal` 仍 +19.2%）。`high/full → low/full` 是**选定的起点**，
  不是搜索发现新最优；不声称成功率提升或搜索空间最优。
- **现场口径**：1 条 live 候选 + 1 条 replay 基线；`scan10` 10 条 replay、
  `candidate-scan` 9 条 replay。页面必须按 `demo_group` + `provenance` 分开标注，
  不得暗示两条都 live。
- **交付边界**：仓库只交付 `web/data` 数据面，不含 HTML 页面；页面由队友 C 消费。

fixture 基线与真实数据差异明显：fixture `solved=3/10`（`molt calibrate` 的校准口径），
真实 Pi `10/10`。fixture 只用于校准检查，不得当作能力声明。

复现 6 组矩阵：以 `v0` 为父，用 `molt.core.genome.child_genome` 生成 switches 变体
（runtime 标 pi/1.5.0），`molt genome verify` 通过后逐组
`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m molt search --scenario demo --runtime pi
--genome <genome.json> --state <独立 state>`；每组 10 题、并发 1。

## 后果

- 页面可以用 `runs[].demo_group` 与 `runs[].provenance` 直接把 closure（1 live + 1 replay）
  与 10 题扫描回放分开渲染，不需要解析 run_id 或时间。
- `demo` 的 live 路径依赖 Pi + trust preflight；auth 不可用时退回 `--mode replay`，
  证据会明确显示 0 live，不存在「假装 live」的中间态。
- 9 条 `candidate-scan` run 会进入 `runs.json`；`--candidate-state` 下它们是已录真实扫描的
  replay，否则是 fixture。页面必须与 live 分开展示。若未来要让候选扫描也全部 live，
  需要新的预算与 ADR，不在本决定范围内。
- `runs.json` 新增 `demo_group` 字段是向后兼容的附加字段；旧导出重新生成即可获得。
- `scenario.json` 的 `claim.live_model_calls` 改为由 evidence 计算（存在 `kind=live` 才为 true），
  并新增 `provenance_counts`；fixture-only 导出的 claim 与旧版一致。
