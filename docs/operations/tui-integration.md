# TUI 集成契约与验收边界

TUI 是 molt 的一个可选调用方，不是 kernel 的组成部分，也不是 Agent runtime。TUI 可以为用户提供项目状态、版本、审计和恢复操作的交互界面，但所有持久状态和事务语义仍由现有 CLI、`KernelClient` 与 Rust kernel 提供。

## 分层约束

- TUI 通过 `molt` CLI 或 Python `KernelClient` 调用现有接口；不得直接读写 kernel state 目录、日志、HEAD 或对象库。
- kernel 只管理不透明对象、manifest、generation、分支、提交、恢复和审计记录；不运行 Agent，不解析业务含义，不持有模型、校园或其他业务凭据。
- TUI 可以展示配置、工具、版本和审计事件，但必须区分原始记录、可重算事实、模型 digest 和未验证推断。
- “提交已保存”只表示 molt 已持久化受管状态；“Agent 已执行”“外部业务已成功”必须来自独立调用方或业务系统证据。
- TUI 的临时缓存、筛选条件和视图状态不属于受管 snapshot，不得伪装成已提交版本。

## 必须保持的事务语义

1. 开始编辑时记录工作区、generation、分支头和固定的初始 snapshot。
2. 保存时使用原基线执行 CAS；过期 generation、分支头或脏编辑必须明确报错并保留编辑内容。
3. 提交响应超时、断线或进程退出后，先用原 request ID 查询或恢复；不得换新 ID 盲重试。
4. 切换或回退只改变本地活动版本。已经固定 snapshot 的旧读者继续读旧版本，新读者才读取新的活动版本。
5. 审计详情必须能从事件定位到版本、原始判断、证据引用和 digest 状态；digest 失败或不可用时原始记录仍可读。
6. TUI 关闭、重启或刷新不能改变 kernel 中已提交的结果，也不能清除待恢复的 request ID。

## 最小验收矩阵

| 场景 | 验收结果 |
| --- | --- |
| 首次连接 | 显示握手得到的 `state_id`，并拒绝连接到预期 state 不一致的服务 |
| 提交 | 通过现有 CLI/client 完成一次合成配置与工具提交，能显示 generation、snapshot 和 request ID |
| 固定读取 | 旧读者跨切换仍读取旧 snapshot；新读者读取新活动版本 |
| 回退 | 回退后新读者读取目标版本，旧读者不变；界面不声称外部业务被取消 |
| 冲突 | 过期基线或分支头提交失败，编辑内容保留，用户可查看冲突原因 |
| unknown 恢复 | 模拟提交前断线和提交后丢响应，重启后使用原 request ID 得到同一结果且不追加 generation |
| 审计 | 按事件查看原始判断、证据引用、版本和 digest；模型推断标明未验证或其证据状态 |
| 权限/完整性错误 | 明确停止并显示修复入口，不静默降级、不改写输入、不跳过校验 |

验收输入必须是合成或脱敏数据，证据放在仓库外独立目录，记录精确命令、工作目录、环境、退出码和源码状态。TUI 的真实热重载、多用户权限隔离、持久登录自启和正式环境接入属于另外的发布门禁，不能由本矩阵代替。

## 接入实现建议

优先复用项目级 CLI 的 `commit-files`、`read-tree`、`switch`、`rollback`、`audit` 和 `recover` 路径。需要更细粒度状态时使用 `KernelClient`，但仍遵守外部集成契约中的 request ID、业务 operation ID、checkpoint 和隐私要求。不得为 TUI 新增绕过既有事务接口的写入口。
