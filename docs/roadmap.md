# molt 发展路线建议

2026-11-21（UTC+8），基于本地源码 `9568a60`、工作区文档和 Linux x86_64 rc8 候选包的既有验收记录。开源是可选择的发展方向，公开范围与发行时间由维护者决定。

## 当前候选包边界

I01–I07 已在本地 rc8 候选包上完成单用户安装、升级与恢复验收。rc8 的验收记录由维护者保管。开发者可按[构建与验包手册](operations/v2-release-checklist.md)从公开源码构建候选包，并记录所用源码和制品的 SHA-256。真实用户管理器中的 transient unit 已演练，持久启用、登录自启、多用户权限隔离和正式环境责任确认仍待专项验收。

**建议将 molt 定位为面向 Agent 工具开发者的本地状态版本与审计工具。** 一套配置、提示词或工具定义常常需要一起变更。molt 把它们和修改理由一起提交。作业在启动时固定一个版本，回退后，新作业可以读取旧配置，已经运行的作业可以继续读原来的版本。首个目标用户是需要回答“这次作业用了哪套文件、为什么改、怎样恢复”的开发者和工作流维护者。

## 1. 先让独立开发者完成第一次接入

首次试用只需一个本地 Linux 工作区和一个能读文件的程序。[入门手册](operations/version-cli.md#安装与首次运行)给了从源码或候选包启动的步骤。[通用示例](operations/version-cli.md#项目级-cli)使用 Bash 和 jq，无需安装 OpenCode、配置模型或提供账号。

1. 在空工作区把 `settings.json` 和 `instructions.md` 作为一组文件，带理由保存 A、B 两版。作业启动时调用一次 `read-tree`，从返回的同一目录读取两份文件，并留存本次快照 ID。
2. 固定 B 后回退到 A。逐份核对新读者看到 A、原读者仍看到 B，并用 B 的事件 ID 找到修改理由。想从 A 接着编辑时，从 A 建分支。回退本身只切换活动快照。
3. 请一位没参与实现的开发者只凭可分享的文档，把同样的步骤用在自己的工具上。记录首次成功读回的耗时、需要口头解释的步骤，以及版本或理由实际帮他回答了什么问题。这个结果用来选下一次改动。首屏入口应与此顺序一致，后续同步中英文 README 时把 OpenCode 例子放在通用路径之后。

本次按当前手册，从源码和含项目 CLI 的 Linux 候选包（SHA-256 `13a09592c1e0f982ff697dbfbc820375bf33c54725881e83863d8aa21ed29930`）各跑了一遍合成示例。旧导出读到 B 的 `full`，新导出读到 A 的 `short`，审计读到 B 的保存理由。下一步验收看独立开发者能否用自己的程序出示两组文件内容、快照 ID 和理由，并说明这解决了什么实际问题。

独立试用的记录格式见[独立试用记录](operations/independent-trial.md)。在维护者授权前，模板只用于合成或脱敏输入的本地演练，不要求接入真实账号或外部服务。

## 3. 如果决定公开分发

- **确认发行范围和第三方声明。** 当前产品采用 MIT。rc8 的源码、wheel 和 Linux x86_64 候选包均需绑定项目许可证正文与 14 个运行时 Rust crate 的第三方许可文本。构建时用锁定依赖图核对声明清单，公开分发前仍需明确历史材料的公开范围。[MIT 许可证](../LICENSE) · [包元数据](../pyproject.toml) · [第三方声明](../packaging/release/THIRD-PARTY-LICENSES.txt) · [构建脚本](../packaging/release/build-linux-x86_64.sh)
- **让安装者能选对制品。** 既有 kernel 发行归档和后续含 `molt project` 的候选包都使用过 `1.1.0` 文件名。给首个拟公开构建分配唯一版本或构建标识，把源码版本、SHA-256、支持平台和可用入口列在同一份发行说明中。用该归档从仓库外完成安装、首次读回、审计和恢复演练。[构建与验证](operations/v2-release-checklist.md)
- **给首批反馈一个可复现的入口。** 沿用贡献指南、CODEOWNERS 和 PR 模板。在公开入口写清如何报告问题，建议附制品版本、最小合成配置、复现命令和期望读到的版本。用一份新检出按贡献指南运行相关测试，验证贡献者仅靠公开材料就能定位和复现问题。[贡献指南](../CONTRIBUTING.md) · [PR 模板](../.github/pull_request_template.md)

下一轮开发优先修复独立接入中实际遇到的第一个障碍。若多个工具都需要程序化访问，再决定 SDK 的稳定范围。若出现跨主机、多人共享的需求，再单独设计身份、授权与部署边界。现有单用户工作区可以先服务于各自独立部署的团队项目。
