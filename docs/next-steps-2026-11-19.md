## 一、结论

建议下一步先完成比赛设计退出与通用底座验收，再以“受控业务操作的状态、证据与恢复”验证 molt 的实际价值。校园 Agent 可以成为首个外部集成场景，但不宜立即把 molt 改造成完整校园平台、身份服务或通用 Agent 框架。

近期最值得验证的问题是：**当 Agent 发起一次业务操作，molt 能否清楚记录谁请求、执行到了哪里、结果是否确定、发生故障后如何继续，以及这些结论依据什么证据。**

身份认证、数据授权、模型调用与校园接口应分别由相应服务负责，不能用状态审计代替这些安全控制。

## 四、优先级 1：定义可独立使用的最小契约

退出完成后，先确认外部程序怎么消费 molt，再考虑新增功能。建议整理一份简短的集成契约，复用已有 kernel API，识别真正的缺口，不先设计大而全的新协议。

契约应回答：

- 外部调用者怎样提交、查询和关联一次任务的记录？
- 哪些状态是调用者自报，哪些来自外部系统核验，哪些只是本地持久化成功？
- request ID、任务 ID、外部业务 ID 分别如何关联？
- 超时、断线、崩溃后怎样查询，何时可以安全重试？
- 证据保存哪些内容、保留多久、谁可读，怎样避免把敏感信息永久写进不可变对象？
- 哪些错误必须停止，哪些允许人工接管？

输出建议是一份集成文档和一个无模型、无校园账号的最小客户端示例。若必须变更 core 或协议，先提出 ADR 与兼容方案，不为示例直接改冻结契约。

验收：独立客户端通过已安装包和真实 socket 完成提交、查询、重启恢复及审计，不依赖源码工作目录。

## 五、优先级 2：先做受控业务模拟，再连接校园系统

建议首个场景为图书馆预约，但第一轮仅使用合成数据和本地模拟服务。验证对象是业务副作用与恢复，不是模型表现。

建议模拟以下路径：

| 情况 | 期望行为 |
| --- | --- |
| 正常预约 | 保留请求、确认、执行结果与业务查询证据的关联 |
| 用户修改日期或座位 | 原确认失效，需要对新参数确认 |
| 提交成功但响应丢失 | 标记结果未知，先查询业务系统，再决定是否重试 |
| Agent 或服务重启 | 从持久状态继续，不能把未知结果当失败重新提交 |
| 无法查询且接口不支持幂等 | 停止自动重试，交由人工核对 |
| 用户请求取消 | 执行单独的取消操作并验证，不用回退本地 generation 冒充取消 |
| 无权限或身份过期 | 由外部授权服务拒绝，molt 记录拒绝事实而非绕过 |

必须区分两层幂等：kernel 同 request ID 的幂等只保护本地提交；校园 API 的去重需要业务接口支持或额外策略。不能由前者推导外部操作“恰好执行一次”。

模拟业务和执行逻辑放在外部集成层或独立示例中，kernel 保持业务无关。实际编码前确认范围与验收，不借此实现 M4/M5。

完成模拟后，再决定是否投入真实校园接口。如果校方授权、接口或数据边界尚未确定，继续保留为模拟验证，不阻塞通用底座建设。

## 六、校园集成的安全分工

建议复用成熟身份系统；密码、TOTP、Passkey、找回与会话管理不由 molt 自研。

| 层次 | 职责 | 与 molt 的关系 |
| --- | --- | --- |
| 飞书入口及身份服务 | 验证来源、关联校园身份、认证与会话管理 | 提供可信的主体关联；不能仅相信 Agent 填写的身份 |
| 授权与确认服务 | 检查资源归属、操作范围、确认有效性 | 在每次执行前强制检查，不由模型或审计结果代替 |
| 模型网关 | 批准的模型路由、数据最小化、出站策略 | 本地模型失效时不擅自切外部 API |
| 执行 adapter 与凭据服务 | 限定业务工具、持有最小权限凭据、查询外部结果 | 不向模型或证据库暴露原始凭据 |
| molt | 保存状态和证据关联、支持审计与恢复 | 不自动证明外部系统结果或执行真实性 |

安全设计优先补充威胁模型：被攻陷的 Agent 能否越权、获取凭据、污染别人的上下文、伪造执行结果或把数据发到任意地址。工具层应采用明确业务操作，不默认提供通用 shell 与任意网络访问。

审计本身也是数据处理：优先保存必要摘要、受控引用及最少字段，明确原始材料的权限和生命周期。哈希不是匿名化或加密；低熵数据仍可能被猜测，日志与错误信息也要检查。

生产需要的隔离、授权或出站控制不满足时应拒绝执行。现有开发或研究模式的显式降级，不能直接沿用为生产安全策略。

飞书消息本身经过飞书服务，即使采用校内模型，也需要校方批准消息内容与外部服务范围。

## 七、M4 的决策时机

暂不把独立 judge 当成校园项目的首要前置项。先确定威胁模型是否确实需要独立执行观察，以及部署是否能提供不同 OS 身份或等效隔离、独立密钥和可信宿主。

如果需求只是“预约是否成功”，业务系统查询通常是更直接的证据。如果需要证明执行过程中观察到了哪些事件，再按 ADR-0016 细化实现方案并单独授权。

独立 judge 也不等于完整沙箱，不替代授权和出站控制，不解决宿主管理员被攻陷的问题。

## 八、建议的工作包与停止条件

以下为顺序建议，不给出缺乏依据的工期，也不代表实现已授权。

| 顺序 | 工作包 | 完成标志 |
| --- | --- | --- |
| A | 比赛设计退出 | 清单确认、依赖解除、通用测试与新包验证完成 |
| B | 最小集成契约 | 明确调用方式、信任边界、错误与恢复语义 |
| C | 模拟业务闭环 | 响应丢失、重启、确认变更和取消等路径可核验 |
| D | 校园接入评审 | 模型、身份、接口、数据范围、责任与运维获得确认 |
| E | 有限真实试点 | 测试账号先行，证据、授权和恢复流程满足验收 |

出现以下情况时，应停止相应扩展并重新评审：需要改变冻结协议、无法隔离用户权限、外部接口无法核验结果、要求未经批准传输个人信息，或要求用存储审计承担未具备的执行真实性保证。

对外沟通可表述为：**molt 提供 Agent 工作流的状态与证据管理基础；校园应用另行集成身份、权限、模型网关和业务接口。最终系统的安全与责任按实际交付和运维范围确定。**
