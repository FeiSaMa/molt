# Agent 模块设计：2026 年的证据与做法

调研日期 2026-11。这一档对应博士排序里的最后一档（harness 组件）。

## 1. 模块设计不是画架构图

真正要划的是四条边界，缺一条就会在运行时长出问题：

| 边界 | 问题 | 划错的后果 |
| --- | --- | --- |
| 上下文 | 每个模块看到什么 | 上下文污染、指令冲突、token 爆炸 |
| 权限 | 谁能产生副作用 | 验证者能改被测对象，判分失效 |
| 状态 | 谁是唯一事实源 | 多份副本漂移，无法归因 |
| 判分 | 谁能下结论 | 自评，奖励作弊 |

常见角色划分是 Planner / Executor / Verifier / Generator（有人写成 PEVG 四契约）。其中最关键的一条：**Executor 是唯一允许产生副作用的角色，Verifier 只读**。判分权和修改权分离，是所有可靠系统的共同点。

## 2. 2026 年的实证：多 Agent 不一定更好

- **Do More Agents? Controlled and Protocol-Aligned Evaluation of LLM Agent Workflows**（arXiv 2606.05670）：在匹配的单 agent 基线下，六个被测多 agent 系统里**最多只有一个**平均超过基线，且那一个的 +1.44 分落在单次运行的 Wilson 置信区间内，等于噪声。
- 同一篇里，真正拉开差距的是 **Claude-Code 风格的 runtime**：66.72% 总分、Level 3 69.23%，比对照高 20 分以上。赢在工具循环和上下文管理，不在 agent 数量。
- **AsynCodeBench**（arXiv 2609.32662）：软件工程任务里，单体编码能力和协作表现之间存在持续差距——把任务拆给多个 agent 并不会自动补上这个差距。

结论：**拓扑不是主要变量，runtime 才是**。这也解释了为什么博士把模块设计排最后：前面的参数、记忆、技能都在这条 runtime 上，先把它们调好，再谈拆不拆。

## 3. 模块正在"下沉进模型"

A Two-Dimensional Framework for AI Agent Design Patterns（arXiv 2605.13850，v2 2026-05）的观察：随着 reasoning model 内化思维链，**架构层的 CoT / planner 模块在贬值**，取而代之的是 budget-aware routing——把"要不要多想"变成路由决策，而不是搭一个规划器。

对设计的含义：每加一个模块，先问它是"模型暂时做不到"的补丁，还是"模型结构上做不到"的补丁。前者会随模型升级消失，后者才值得长期维护。

## 4. 模块清单

| 模块 | 是否必需 | 证据 | 什么时候拆 |
| --- | --- | --- | --- |
| 主循环（tool loop） | 必需 | Claude-Code 风格 runtime +20 分 | 不拆 |
| 工具接口（ACI） | 必需 | SWE-agent +10.7 分 | 不拆，改接口 |
| 上下文管理（压缩/卸载） | 必需 | context rot、SoL-Pi | 不拆，调参 |
| 路由/升级 | 强烈建议 | 成本差一个数量级 | 独立模块 |
| 验证器 | 必需（有副作用时） | 评估器论文 | 独立进程，只读 |
| 子 agent | 可选 | 只在上下文隔离有收益时 | 见下 |
| 记忆库 | 第二档 | 见 memory-models | 独立存储 |
| 技能库 | 第三档 | 见 skill-evolution | 独立目录 |
| 沙箱 | 安全边界 | 不是能力模块 | 独立环境 |

### 子 agent 的判据

只有满足下面两条之一才拆：

1. **需要独立上下文**：子任务会往里灌大量无关材料，放进主上下文会污染后续判断；
2. **需要并行**：子任务之间没有依赖，且墙钟时间重要。

编码类任务通常两条都不满足——改同一个仓库的多个文件是紧耦合的，拆出去反而要反复同步状态。LangChain 那篇 *Organizing Context in a Multi-Agent Harness* 也是这个结论：subagent 的价值是 context isolation，不是"分工"。

## 5. 四条设计规则

1. **一个模块只有在"独立上下文"或"独立权限"时才值得拆**，否则合并。每次跨模块传递都要重建上下文，token 和错误率一起涨。
2. **判分权与修改权必须分离**。Verifier 不能改被测对象，也不能看 holdout。
3. **状态有唯一事实源**。所有模块读写同一份存储，不要各自缓存一份。Cognition 那篇 *Don't Build Multi-Agent Systems* 的核心教训就是这个。
4. **优先改接口，不拆角色**。SWE-agent 的 10 个点来自接口细节，不是来自多 agent。

## 6. 对 molt 的落点

molt 不该造模块——Pi 已经提供了主循环、工具、compaction、subagent、skills、MCP、沙箱。molt 能做的是把这些**变成可搜索的开关**：

```text
subagent         开 / 关
tools            四件套 / 精简 / 扩展
mcp              开 / 关
skills           开 / 关
sandbox          开 / 关
```

但按证据，这一档的收益最小：大部分"模块"要么是模型能力的临时补丁，要么被 Claude-Code 风格的 runtime 默认吃掉。真正值得进搜索空间的只有 **路由/升级**（便宜模型兜底、失败换强模型），因为它的成本杠杆最大，而且需要外层的重试与记账才能实现——这恰好是 molt 的强项。

所以模块设计这一档在 molt 里的正确形态是：**只做开关，不做实现；只搜路由，不搜拓扑。**
